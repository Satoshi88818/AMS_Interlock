Status: Discrete-event software simulation of the FPGA gate, edge node, and cloud interacting under realistic timing, crashes, and network loss. NOT a substitute for hardware-in-the-loop testing or an RTL implementation. Purpose: catch integration-level design mistakes — the ones that only show up when the three actors interact under real timing pressure — before they become expensive hardware-bench debugging sessions.

This document — simulating the FPGA and edge as interacting hardware, not just testing the state machine's logic alone

1. Why Simulate Hardware When the State Machine Is Already Tested

Every prior test suite validated the InterlockStateMachine in isolation: given a sequence of events, does it transition correctly? That's necessary but not sufficient. It cannot catch bugs that only exist in the interaction between actors running at different cycle rates — specifically, the gap between "the FSM object's .state attribute changed" and "the physical FPGA gate hardware actually reflects that change." Those two things are not the same event in a real system, and the delay between them is exactly where a hazard can live undetected by unit tests.

This simulation found two such bugs that no prior test suite could have caught, because they only exist at the interaction layer:

2. Findings

2.1 Design finding: permit-refresh rate vs. permit-max-age (found before any bug-hunting — from just building the model)

The original spec describes edge (Jetson) inference running at ~1ms cadence, while permit_max_age_us defaults to 50µs — roughly 20x tighter. If the same loop that runs full motion/dose inference is also responsible for refreshing the gate permit, the gate cannot stay continuously open — it will flicker closed between refreshes, because each permit goes stale long before the next one arrives. This simulation reproduces that failure directly and deterministically (test_gate_flickers_if_permit_refresh_slower_than_max_age).

Implication for the real implementation: "decide whether to hold or deliver" (slow, ~1ms, full inference) and "refresh the gate permit" (fast, must run well under permit_max_age_us) must be two separate loops. The fast loop simply re-asserts the slow loop's last decision at high frequency; it does not re-run inference.

2.2 Bug found by testing: permit-revocation latency on hazard detection (tolerance-exceeded path)

Initial version of the simulation only refreshed/revoked the FPGA's held permit on the periodic edge-cycle schedule. When a motion-tolerance excursion was detected between scheduled refreshes, the FSM correctly transitioned to HOLD immediately — but the FPGA kept honoring the previous, still-technically-valid permit until it aged out on its own. Net effect: the physical gate could remain open for up to one edge-cycle period after the software had already decided to stop, a real safety gap invisible to any test that only checks the FSM's .state attribute.

Fix: permit revocation on a hazard-detecting event (tolerance exceeded, manual stop) must happen immediately, synchronously with the event — not wait for the next scheduled refresh. Refresh-on-schedule is correct for the steady-state "still fine, keep going" signal; revoke-on-event must be immediate. Implemented as an explicit immediate re-sync call at each hazard-detecting event site.

2.3 Second bug found by broader fuzzing: the same gap existed on the heartbeat path

After fixing 2.2, a wider property-test run (raised from 150 to 1500 examples specifically to hunt for this) found the identical class of bug on a different path: resuming from DEGRADED_EDGE_ONLY back to HOLD (a legitimate transition — see FMEA #1's design — occurring when the cloud reconnects with a matching plan hash while the edge was in HOLD before it degraded) also failed to immediately revoke the permit, leaving a stale-but-valid permit open for up to one edge-cycle after resuming into a gate-closed state.

Fix: the same immediate re-sync now also fires after every heartbeat-driven event, not just the tolerance/manual-stop paths. General principle extracted from finding this twice in two different places: any code path that can change fsm.state must immediately re-sync the held gate permit — this should be enforced structurally (e.g., a single choke point all state-changing calls flow through) in a production implementation, rather than remembered at each call site as was done here for the simulation.

3. Validation Method

Beyond the scenario-specific tests (normal operation, edge crash, heartbeat loss/recovery, degraded-budget exhaustion, plan-hash mismatch, manual stop, tolerance excursion), the capstone test is a property-based fuzzer that randomizes network drop probability, motion-excursion timing, and edge-crash timing simultaneously, and checks one integration-level invariant on every single simulated timestep:

The physical gate must never be open while the logical FSM state says it shouldn't be.

This is the same invariant already proven structurally against the FSM in isolation (test_interlock_properties.py), now re-checked against the simulated hardware's actual behavior — closing the gap between "the state machine's logic is correct" and "the hardware built around it actually behaves that way." Both bugs above (2.2 and 2.3) were caught by this exact test, at two different points during development, after raising the search budget specifically because a full-fidelity check like this benefits from more exploration, not less.

4. Scaled Time Notice

All default timing constants used in the simulation (hold_timeout_ms, degraded_max_duration_s, heartbeat_interval_us, etc.) are scaled down uniformly from the placeholder values used elsewhere in this project, purely so the simulation runs quickly in a Python discrete-event loop. The ratios between values — especially permit-refresh-rate vs. permit_max_age_us — are what matter and are preserved; the absolute values here are not clinically meaningful and must not be copied into a real config.

8. What This Still Does Not Close

This is a software model of hardware behavior, built to find design and logic bugs cheaply. It does not, and cannot, validate:

Actual FPGA/RTL timing — real logic propagation delays, clock-domain-crossing metastability, and register setup/hold times are not modeled here at all. The 10µs/50µs/20µs figures used are illustrative round numbers, not derived from any real FPGA timing analysis.

The physical shared-counter hardware from the clock synchronization design — this simulation assumes it exists and works; whether it's feasible on the actual rack design remains the open hardware item flagged previously.

Real network behavior — UnreliableNetwork models independent i.i.d. packet drops, which is a simplification; real WAN links have correlated bursts, variable latency (not just binary deliver/drop), and reordering, none of which are modeled.

The single-choke-point recommendation from Section 2.3 — this simulation fixed the bug by adding re-sync calls at each of the three call sites found so far; it does not implement or test the more robust structural fix (a single function all state changes flow through) that the finding itself recommends for the real implementation.

9. Recommended Next Step

Implement the single-choke-point pattern recommended in Section 2.3 — route every method on InterlockStateMachine that can change .state through one wrapper that also handles permit re-sync as a side effect, rather than relying on call-site discipline (which is exactly what failed twice here, in two different places, during this exercise). This closes the pattern of bug found, not just the two specific instances discovered so far, and is more likely to survive future changes to the state machine without silently reopening the same class of gap.
