AntimatterSim v10 — Clock Synchronization Design (Tier 0, FMEA #5)

Status: Software reference model and validated design pattern. Closes FMEA #5 ("clock domain skew between FPGA, edge, and cloud") at the software-contract level. Physical hardware implementation (which oscillator, which bus, whether a shared-counter link is feasible in the actual rack design) remains an open hardware item — see "What This Does NOT Close" below.

1. The Wrong Instinct, and Why

The obvious response to "the FPGA, edge, and cloud don't share a clock" is "synchronize the clocks" — run NTP or PTP everywhere and move on. That's the wrong fix here, for two different reasons at the two different boundaries:

FPGA ↔ Edge needs agreement at the ~50µs scale (permit_max_age_us). Standard NTP is roughly 1000x too coarse. Even hardware-timestamped PTP over a real network path is fragile — it depends on hardware timestamping at every hop, a stable grandmaster, and minimal path asymmetry. If sync quality silently degrades, the effective safety margin silently widens without tripping any explicit fault. Trying to hit a 50µs budget via a synchronized-but-independent clock is solving a harder problem than necessary.

Edge ↔ Cloud spans a WAN with variable latency and jitter. Tight synchronization is not just hard, it's the wrong tool: heartbeat liveness and plan identity don't actually require the two sides to agree on wall-clock time at all.

The design below picks a different solution for each boundary based on what it actually needs, rather than applying one synchronization scheme everywhere.

2. Governing Principle

Every time-based safety decision is made using only the local clock of the actor making that decision. A timestamp or clock reading from another actor is never used as an input to a safety-timing decision. Cross-actor time is used only for audit-log correlation, where its uncertainty is explicitly bounded and reported — never assumed exact.

3. FPGA ↔ Edge: Shared Counter, Not Synchronized Clocks

Instead of synchronizing two independent clocks to hit a 50µs budget, the design sidesteps the synchronization problem: the FPGA and edge SoC read the same physical counter — a free-running hardware counter on the treatment-head backplane, exposed to both sides via a memory-mapped register or a direct low-latency link (not a general network segment). This isn't "kept in sync," it's literally one clock, read twice. There is no skew to compensate for by construction.

The edge issues a GatePermit timestamped in this shared tick domain.

The FPGA validates the permit with a single integer comparison against the same shared counter — no unit conversion, no skew-compensation term, because none is needed.

Fallback if a shared-counter link isn't feasible in the actual rack design: hardware-timestamped PTP over a dedicated point-to-point link (not switched Ethernet), with an explicit, continuously monitored sync-quality metric that itself feeds a fault condition if it degrades. This fallback is not implemented in this reference model — it's flagged as a hardware/network open item below, since it depends on decisions (link topology, PTP hardware support) outside software's control.

""" Clock-domain design for the Tier 0 interlock. GOVERNING PRINCIPLE: Every time-based SAFETY decision is made using only the local clock of the actor making that decision. 4. Edge ↔ Cloud: Deliberately Not Synchronized for Safety Purposes

The existing interlock design (from the Tier 0 interlock spec) already has this property, and this exercise makes it explicit and tests it directly rather than leaving it as an implicit accident of the API shape:

cloud_heartbeat_missed() and cloud_heartbeat_received() take no timestamp argument at all. Whether a heartbeat was "missed" is determined entirely by the edge's own local monotonic clock measuring elapsed time since it expected one — the cloud's clock value is never consulted.

Plan identity on reconnect is checked by content hash, not by timestamp comparison — this is why the no-auto-reconcile rule (FMEA #1) doesn't require edge and cloud to agree on time at all, only on the hash of the plan they're each looking at.

A loosely-synchronized NTP/PTP-over-WAN time is assumed to exist for audit-log readability only (so a human reviewing logs from both sides can roughly align events), and is never read by any safety-decision code path.

5. Tests: Proving Skew Independence, Not Just Asserting It

The value of this exercise isn't the design prose above — it's proving the code actually has this property rather than just being described that way. The tests below inject deliberately absurd, physically nonsensical clock values for the "other" actor and confirm the outcome never changes, because the value is never consulted — not because it was correctly compensated for.

7. What This Does NOT Close

This closes FMEA #5 at the software contract level: the code cannot be made to leak one actor's clock into another actor's safety decision, and that's now enforced by both structure (method signatures) and tests, not just convention. It does not close:

Physical feasibility of the shared counter for the actual rack/hardware design — that's a hardware engineering decision (oscillator choice, register-access latency, backplane design) that this software model assumes exists but cannot itself validate.

The PTP fallback, if a shared counter turns out not to be feasible — not implemented here; would need its own design and its own sync-quality-degradation fault path.

Silent hardware failure of the shared counter itself (freeze, wrap, desync at the hardware level) — that failure mode belongs in the hardware FMEA, not this software one. Worth flagging explicitly to whoever owns that FMEA so it doesn't fall into the gap between the two documents.

Audit-log clock-offset estimation process for edge↔cloud — this design says such offsets should be recorded with explicit uncertainty bounds for post-hoc log correlation, but the actual sampling/recording mechanism isn't specified or implemented yet.

8. Recommended Next Step

Take the shared-counter hardware feasibility question to whoever owns the treatment-head rack design — it's the one item here that this software work cannot resolve on its own, and everything else in this design depends on knowing whether that link is achievable as specified.
