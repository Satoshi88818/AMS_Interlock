2. What Changed From the Original Spec During This Exercise

Building and testing this reference implementation surfaced four concrete defects/gaps that were not visible from the spec document alone:

Falsy-zero bug (FMEA #3) — found by the very first run of the example-based test suite.

Reactive-only budget checks (FMEA #2) — found by design review while writing tests; led to adding tick().

Unvalidated negative dose input (FMEA #4) — found by re-reading the implementation for the FMEA.

Property-test budget was initially insufficient (FMEA #10) — an intentionally-injected bug (silent auto-reconciliation on plan-hash mismatch) passed a 200-example/60-step property test run, and only failed reliably once the budget was raised to 500×80. This is itself a finding: stateful property tests over safety-critical logic should document the search budget that reliably reproduces known-bad behavior, not just "tests pass."

This pattern — spec review misses things that executable tests catch, and low-budget property tests miss things that higher-budget runs catch — is the core argument for doing this work before hardware, not after.

3.1 Invariants checked continuously by the property tests

The FPGA gate may only be open in DELIVERING or DEGRADED_EDGE_ONLY — checked structurally against gate_may_be_open().

FAULT and MANUAL_STOP can only be exited via RECOVERY — no direct path back to an operating state.

HOLD can never transition directly to COMPLETE.

DEGRADED_EDGE_ONLY can never jump directly to ARMED or COMPLETE.

The audit log is internally consistent (chained transitions, non-decreasing timestamps).

3.2 Oracle-based check (not a generic invariant)

The plan-hash reconciliation rule is checked against an independent oracle tracked by the test harness itself (not by reading the implementation's internal state), specifically because this is the rule an FMEA-level review identified as highest severity (FMEA #1). This is the check that caught the intentionally-injected regression described in Section 2.

4. Caveat on Property-Based Testing

Property-based testing with random search is not exhaustive verification. During development of this suite, an intentionally-injected safety violation (silently resuming DELIVERING on a mismatched plan hash, instead of FAULT) passed a property-test run configured for 200 examples × 60 steps, and only failed reliably after raising the budget to 500 × 80. The example-based test targeting that exact scenario caught it immediately in both configurations.

Conclusion for reviewers: treat the example-based suite as the primary specification-conformance evidence (it is deterministic and maps 1:1 to spec rows), and the property-based suite as a secondary, probabilistic search for unanticipated interactions — valuable, but not a substitute for either the example suite or an eventual formal verification pass (e.g., model checking with TLA+ or similar) before hardware integration.
